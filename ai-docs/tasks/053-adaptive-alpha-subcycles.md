# 053 — 自适应 alpha 子循环表（nSubCycles 的 Function1）

- 状态：done（2026-09-14：自适应表阴性（−2%，机理=填充期占 95–99% 步数）；顺带量化了修正遍数与前沿精度的取舍）
- 优先级：P1
- 依赖：052（上游路径事实：`nAlphaSubCycles = ceil(nSubCycles(alphaCoNum))`）、048/050
- 预估规模：1 天
- 来源：052 读源码时发现的未探索旋钮——契约的 `alpha.melt.* nSubCycles`
  写的是**常数 8**，但上游把它当 `Function1` 在**界面库朗数**上求值。

## 1. 背景与现状

- 上游（OF14 `twoPhaseSolver::alphaPredictor`）：
  `nAlphaSubCycles = ceil(nAlphaSubCyclesPtr->value(alphaCoNum))`，
  `alphaCoNum` 是该步的最大界面库朗数（`twoPhaseVoFSolver::correctCoNum`
  在 preSolve 算出）；
- 契约（v1.29）里 `nSubCycles 8`（常数）→ **所有相位**都用 8 个子循环，
  每个子循环做一次 `alpha1Eqn.solve()` + `correctInterface()`（曲率）；
- 相位差异很大：填充期界面库朗被 `maxAlphaCo 0.015` 钉住（子循环保护
  有意义）；**保压/冷却期界面近乎静止**（alphaCoNum ≪ 0.015），8 个子循环
  几乎不改变结果，纯属重复开销——052 已证明"修正遍数"能吃掉 ~30% 墙钟，
  子循环是同族（每次子循环 = 一次完整 alpha 输运 + 曲率）；
- 上游文档语境：子循环的目的通常是让**子循环内**的界面库朗 < ~1；
  契约的 0.015/8 ≈ 1.9e-3 远低于该限，说明 8 是精度余量而非稳定性下限
  （032 的 nSubCycles 8↔16 对照也显示守恒仅差 3.3%）→ 在库朗小的相位
  减子循环的风险可控。

## 2. 目标

用 `Function1 table` 替代常数：

```
nSubCycles
{
    type    table;
    values
    (
        (0      1)     // 界面静止：1 个子循环
        (0.002  2)
        (0.008  4)
        (0.015  8)     // 界面库朗顶到 maxAlphaCo：保持契约的 8
    );
}
```

即**高库朗端不动**（填充期行为不变，保守），只压缩安静相位。

1. 实测 I（自适应表）vs F（v1.29 常数 8）在同会话的墙钟、步数、守恒、
   完整验收；
2. 附相位分解（填充/保压/冷却各占多少步），验证收益来自安静相位；
3. 结论：可用 → 走契约修订建议（v1.30）；不可用 → 记录阴性。

## 3. 技术方案

- 变体：`scripts/lever-experiment.sh` 增 `I`（F 的全部设置 + 表格式
  `nSubCycles`），patch 需替换整段 `nSubCycles 8;` 行为 dict（数值型
  `patch_block` 不适用，改为在 alpha 块内做整行替换）；
- 相位分解：从 `log.foamRun` 的 `moldingFoam: filling/packing` 打印与
  V/P 切换/闸口封冻/顶出事件时间戳，按 `^Time = ` 计数分箱；
- 每档 ≥2 样本（VM 方差 ±11%），守恒是确定量（1 样本即可定值）。

## 3a. 实测与结论（2026-09-14，契约 case @4 子域，同会话）

| 变体 | 设置 | 墙钟 (s) | 步数 | 守恒 | 验收 |
|------|------|----------|------|------|------|
| F 基线（v1.29） | 8 子循环 / 1 修正遍 | 467 | 15,212 | 5.010e-04 | PASS |
| **I 自适应表** | 库朗表 1→8 / 1 修正遍 | **455 / 460** | 15,214 | 5.010e-04 | PASS |
| J 精度优先 | **12 子循环** / 1 修正遍 | 539 | 15,214 | 4.979e-04 | PASS |

**结论 1（阴性）**：自适应子循环表只快 **~2%**（在 VM 方差 ±11% 内），
不值得引入 Function1 表带来的数值面。原因由相位分解给出：

| case | 填充期步数占比 | 说明 |
|------|----------------|------|
| 契约 | **97–99%** | 填充期 dt 被界面库朗钉小（0.015），步数集中在填充 |
| Kairos 实件 cli10 | **95%** | 同上（其 `maxAlphaCo 0.1` 亦然） |

即**安静相位（保压/冷却）在步数上只有 3–5%**，且这些步里子循环本身
也不是主要成本（I 把安静相位的子循环从 8 降到 1–2，总墙钟几乎不动）
→ 表的理论上限就是几个百分点。**不采用。**

**结论 2（顺带量化，052 的延伸）**：`nCorrectors` 的减半换来 −30% 墙钟，
但会损伤**前沿对称性**这一契约验收看不到的指标。用 `weldLine` 用例探针
（其自身设置 6 子循环）实测：

| (nSubCycles, nCorrectors) | 熔接痕对称性误差 | 契约档墙钟 |
|---------------------------|------------------|-----------|
| (6, 2) 用例原设置 | 0.554% | — |
| (6, 1) | **1.226%**（2.2×） | 467 s（契约 8/1 实测） |
| (12, 1) | **0.829%**（1.5×） | 539 s（+15%） |

→ 取舍明确：**要最快取 (8,1)（v1.29 缺省 ✓）；要前沿/熔接痕保真度取
(12,1)（+15% 墙钟，恢复约 60% 的损失）；(6,1) 是最激进档**。该结论对
**Kairos 的 case 模板**（其 fvSolution 为 `nCorrectors 2 / nSubCycles 6`）
可直接套用：想拿 −30% 就改 (6,1)，想稳妥取 (12,1)。契约本体维持 v1.29。

## 3b. Kairos 实件 bench（2026-09-14，cli10 @4 子域，当前源码构建）

在真实件 case（cli10，2.5k 单元级、其模板设置 `nSubCycles 6 /
nCorrectors 2`、`maxAlphaCo 0.1`）上只改这两个旋钮：

| (nSubCycles, nCorrectors) | 墙钟 | 步数 | 质量预算残差 | V/P 切换 |
|---------------------------|------|------|--------------|----------|
| (6, 2) 模板原设置 | 74 s | 5,069 | **−3.76e-05 kg** | fill 0.96072 @ 1.08019 s |
| (6, 1) | **64 s（−14%）** | 5,094 | +1.42e-04 kg | fill 0.96080 @ 1.08016 s |
| (12, 1) | 84 s（+14%） | 5,091 | +1.97e-04 kg | fill 0.96008 @ 1.07906 s |

- 收益随**界面工作量占比**缩放：契约 case（14k 单元）−30%，实件（5k 单元）
  −14%；更大的件预期介于两者之间或更好；
- `nCorrectors 1` 的代价在实件上表现为**质量预算残差 3.8e-05 → 1.4e-04 kg**
  （相对约 2e-4）与熔接痕对称性（见 3a，探针 0.554% → 1.226%）；
- **`(12,1)` 在实件上比原模板慢 14%** → 不要盲目靠加子循环"补精度"，
  要按件权衡；
- 物理路径稳定：三种设置的 V/P 切换时刻与方法一致（fill ≈0.960，
  t ≈1.080 s）✓。

## 6. 风险与缓解

- 安静相位减子循环会改变界面的数值扩散 → 守恒与 acceptance 都要过
  （1e-3 阈值）；此外检查 `weldLine`/`fountainFlow` 类硬指标（本轮先跑
  契约；用例层面留给 v1.30 落地后的 test-solver 回归）；
- 表格线性插值 + `ceil` 的组合在插值段会给出非整数期望值 → 表值按
  "该库朗下期望的子循环数"写，ceil 只向上取整，不引入额外保守性。
